## Stage 8 เริ่มด้วยการอัปเดต knowledge ก่อน (ยิงอันนี้ก่อนเสมอ)

```text
Before Stage 8, append these sections to @wikillm\sources\knowledge.md so they persist across sessions.

## Unity scene model
- `Persistent.unity` loads first and is NEVER unloaded. It hosts RootLifetimeScope,
  the main Camera, the HUD canvas, and all app-lifetime singletons.
- Gameplay scenes (Village=1, Shop=2, AuntieHouse=3, FarmPlot=4) are loaded ADDITIVELY,
  one at a time, and unloaded only after the replacement is live.
- Every gameplay scene has exactly one `XxxLifetimeScope` whose parent is RootLifetimeScope.
- Scene ids in the enum MUST match the scene_id column in data/pond.csv.

## UX contract for on-chain actions
- No user-facing action may block the UI thread waiting for a block.
- Every action shows: immediate local feedback -> "confirming" indicator -> confirmed or rolled back.
- If the chain is unreachable, the game stays playable in read-only mode and says so clearly.
- If the presence hub is unreachable, the game runs in single-player visual mode and says so.

## Editor-generated content
- Scenes, prefabs and ScriptableObject assets are produced by editor scripts under
  `Assets/Main/Editor/`, never by hand, so they can be regenerated and reviewed in git.
- Art is placeholder: solid-colour sprites generated at runtime/import time.
  Real pixel art is dropped in later and must not require code changes.
```

## Stage 11 — Optimistic UX + reconciliation (สำคัญที่สุด)

```text
Stage 11 — Make the chain feel instant. This is the highest-risk UX stage; be thorough.

1. `Infrastructure/Blockchain/OptimisticState.cs`:
   - Holds a confirmed snapshot (from StateWatcher) plus an ordered list of pending local
     mutations, and exposes a merged view that the UI binds to.
   - `IDisposable ApplyPending(PendingMutation m)` — e.g. bait -1, stamina -5, gold -50.
   - On confirmation: drop the pending entry, adopt the confirmed snapshot, and if the two
     disagree beyond a tolerance, log a reconciliation warning with both values.
   - On failure or timeout: drop the pending entry and raise `OnRolledBack(mutation, reason)`
     so the UI can toast "ยกเลิกรายการ: <reason>" and restore the display.
   - NEVER let optimistic state be read by anything that decides legality — it is display only.

2. Upgrade `ActionQueue`:
   - Serialize submissions per avatar so nonce ordering is never violated.
   - Track state machine per item: Queued -> Staged -> Confirmed | Failed | TimedOut.
   - Retry policy: retry twice on transport errors with backoff, never retry on a validation
     exception thrown by the action itself.
   - Expose `IReadOnlyList<PendingAction> Pending` and events for the HUD indicator.
   - Persist nothing to disk; on app restart the queue starts empty by design.

3. Reorg handling in `StateWatcher`:
   - Subscribe to tip changes; detect when the new tip is not a descendant of the previous
     tip, and in that case re-read all watched state from scratch and raise `OnReorg(depth)`.
   - Debounce state reads: at most one full read per tip, and only re-read the accounts that
     the incoming block actually touched when that information is available.

4. `ChainConnectionMonitor`:
   - States: Bootstrapping, Syncing (with block height progress), Synced, Stalled
     (no new tip for 3x the target block interval), Offline.
   - Drives the HUD dot from Stage 9 and blocks action submission with a clear message
     when Stalled or Offline, instead of letting actions silently time out.

5. Wire every existing presenter (Fishing, Shop, TaskBoard, Kitchen) through OptimisticState
   so the inventory and stamina numbers move the instant the player clicks.

Deliver a short document `docs/UX-CHAIN-CONTRACT.md` with a sequence diagram in plain text
for one fishing cast, from click to confirmed catch, including the failure branches.
```

## Stage 12 — Presence polish

```text
Stage 12 — Make other players feel present and correct.

1. `RemotePlayerView`: position interpolation with a 150ms buffer (store the last 3 snapshots,
   render interpolated past state), snap when the error exceeds 2 tiles, drive the Animator
   from the received AnimationState, and flip the sprite by Direction.

2. `NameTagView`: display name plus a shortened avatar address (first 4 hex chars),
   always upright, clamped to the screen edge when off-view.

3. Pond occupancy UI:
   - HubServer broadcasts `OnPondHint` whenever a player enters or leaves a FishingSpot
     trigger in scene 4, listing occupant display names.
   - `PondHintView` floats over the pond: "2/2 คนกำลังตกปลา" and turns red when full.
   - CRITICAL: this is a hint only. The Fishing flow still calls OccupyPondAction and must
     handle PondFullException even when the hint said a slot was free. Add a comment saying so.

4. Emotes: 6 emotes bound to the number keys, sent via `EmoteAsync`, rendered as a sprite
   bubble for 2 seconds. Rate-limit to 1 per second per client AND per connection on the server.

5. Local player movement: `PlayerInputController` with 8-way input, tile-aligned collision,
   and a `PresenceBroadcaster` that calls `SendMove` at 10Hz or immediately on
   direction/animation change, exactly as specified in knowledge.md.

6. Server hardening in HubServer:
   - Reject a move whose delta implies more than 2x the max walk speed since the previous
     update from that connection; clamp instead of disconnecting, and log it.
   - Cap displayed name length at 16 characters and strip control characters.
   - Add a per-connection heartbeat; evict and broadcast OnLeave after 30s of silence.

7. Add an EditMode test for the interpolation buffer maths and the speed clamp.
```

## Stage 17 — Balance sim + release

```text
Stage 17 — Prove the economy holds, then freeze for closed test.

1. New console project `src/ProjectF.Sim/` (net8.0, references ProjectF.Lib and Tables):
   - Simulates N virtual players over M blocks against an in-memory world, using the real
     action classes — never a reimplementation of the rules.
   - Player archetypes: casual (20 actions/day), regular (60), grinder (200).
   - Outputs a CSV and a markdown report: gold supply over time, gold sources vs sinks,
     inventory accumulation per item, time-to-level curves for fishing and cooking,
     pond contention rate (how often OccupyPond fails) at 10/25/50 concurrent players,
     and stamina utilisation.
   - Flag these as warnings: gold supply growing faster than 5% per simulated day with no
     matching sink, any level taking more than 3 days of regular play, pond failure rate
     above 30%, any item that is never consumed by any recipe or task.

2. Run the sim at 20, 50 and 100 players. Produce `docs/BALANCE-REPORT.md` with the numbers,
   your interpretation, and a concrete list of proposed CSV value changes. Do not change
   the CSVs yet — present the diff for my approval first.

3. Security and integrity pass over ProjectF.Lib:
   - Confirm every action validates the signer, validates every id against the tables,
     clamps every numeric input, and cannot produce a negative balance or count.
   - Add property-based tests (FsCheck or a hand-rolled fuzzer) that throw random and
     malformed PlainValue payloads at every action and assert that the world is either
     unchanged or changed legally — never corrupted, never an unhandled exception type.
   - Verify nothing in Lib can be exploited by replaying an identical transaction.

4. `/review` the entire repository against @knowledge.md and report a table of findings by
   severity, then fix everything at high and medium severity.

5. Ship the closed-test package:
   - `docs/RELEASE-CHECKLIST.md` — build, validate, smoke test, tag, package.
   - `docs/PLAYER-GUIDE-TH.md` — Thai instructions for testers: install, create a character,
     enter the peer string, the core loop, known issues, and how to send me their log folder.
   - `docs/KNOWN-ISSUES.md` and a bug report template.
   - Tag v0.1.0-closed-test and summarise everything that is still stubbed or faked,
     especially anything a tester might mistake for a finished feature.
```
