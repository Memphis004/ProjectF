# Sign-In Screen & Two-Node Peer Sync

This note documents the sign-in screen added to `planet-clicker`, why it was
built the way it was, the root causes of the peer-sync problems uncovered
along the way, and how to run the reusable two-node end-to-end test.

## What was added

| File | Purpose |
| --- | --- |
| `Assets/_Script/SignInController.cs` | Sign-in screen controller (keystore dropdown, Secret field, Sign-in gating). |
| `Assets/Scenes/SignIn.unity` | New first scene. Generated by the editor utility below; re-runnable. |
| `Assets/LibplanetUnity/Editor/SignInSceneBuilder.cs` | Editor menu **Tools → Libplanet → Build Sign-In Scene**: rebuilds the scene and pins it first in Build Settings. |
| `Assets/LibplanetUnity/Agent.cs` | `SetPendingPrivateKey()` / `HasPendingPrivateKey`, unified identity resolution, `--host/--port/--peer` support, non-fatal preload, CoMiner tip-race retry. |
| `Assets/LibplanetUnity/Helper/Options.cs` | `privateKey`, `host`, `port` options + hand-rolled command line parser. |
| `Assets/_Script/Game.cs` | Defers `Agent.Initialize` until sign-in completes; `--auto-click` dev hook. |
| `planet-clicker/run-two-nodes.ps1` | Two-node E2E test script (see below). |

Flow: `SignIn.unity` → the player picks an address, enters a Secret, presses
**Sign-in** → `Agent.SetPendingPrivateKey(key)` → `Game` scene loads →
`Agent.Initialize()` consumes the pending key.

## Approach: encrypted keystore (same as the reference)

`gamejam-laylas-island`'s `IntroCanvas` uses **Web3 Secret Storage**:
`ProtectedPrivateKey.Protect(key, passphrase)` saved into
`Web3KeyStore.DefaultKeyStore`, an address dropdown of stored keys, a masked
Secret field holding the *passphrase*, "Create New One" to generate + protect a
fresh key, and wrong-passphrase handling via `Unprotect` failure.

The bundled Libplanet 0.38 DLLs already contain `Libplanet.KeyStore.*`, so
`planet-clicker` now matches that model exactly (no new dependencies):

- **Dropdown** lists remembered addresses from the platform keystore
  (`Web3KeyStore.DefaultKeyStore`), plus two special entries:
  - **Enter private key** — paste a raw 64-hex-char private key (validated live;
    the Sign-in button only enables for well-formed keys).
  - **Create New One** — generates a fresh key; whatever you type becomes its
    passphrase and the encrypted entry is saved to the keystore.
- **Secret field** is masked (`Password` content type) for keystore/passphrase
  modes, plain for raw-key mode.
- **Sign-in fails loudly but safely**: wrong passphrase → inline red error;
  malformed raw key → inline error; the button never silently no-ops.
- Keys validated by constructing `new PrivateKey(ByteUtil.ParseHex(hex))` and
  catching failures (correct length/decodability checked for free).

Rationale: it matches the reference UX exactly, uses infrastructure already
shipped in the DLLs, and is strictly more capable than raw-key-only (raw keys
remain available via the "Enter private key" entry for tests).

`--private-key` still works end-to-end: when present, the sign-in screen skips
itself and loads `Game` directly, and `Agent.ResolvePrivateKey()` uses that key
(precence: pending sign-in key → `--private-key`/clo.json → saved key file →
freshly generated).

## Root causes found & fixed

### 1. Every copy of the game had the same address

`Agent` persisted its key to `Application.persistentDataPath/private_key`,
which on Windows is `%USERPROFILE%\AppData\LocalLow\Planetarium\planet-clicker\private_key`
— **shared by every copy of the game on the machine** (keyed by Company Name +
Product Name, not by install path). Nothing was read from `--private-key`
because the `Options` class had no `privateKey` field at all (EXAMPLE.md was
aspirational).

**Fix**: sign-in screen provides the key explicitly; `--private-key` is parsed;
per-node `--storage-path` separates chain data; two instances of the *same*
build now get distinct addresses deterministically.

### 2. `--peer` never worked: options were silently dropped

`Options` also lacked `host`, `port`, and `peer` attributes, so seed peers were
never parsed and `BootstrapAsync` was called **without any seed peers**
(the "All seeds are unreachable" you saw was Libplanet's message for an *empty*
seed list). The bundled CommandLineParser library additionally throws while
instantiating the options type in this environment, so parsing is now a small
hand-rolled switch (Unity's own `-logFile`, `-batchmode`, … args are ignored).

### 3. `InvalidBlockIndexException` in `CoMiner`

`MineBlock` captures the tip when it starts; if the tip moves while mining
(a synced block or another mining pass), the append fails. With difficulty in
the 100k+ range the race was rare, and it is **benign** — the block is dropped,
staged txs remain staged for the next pass, no state corruption occurs. It
looked worse than it was. The miner now detects
`InvalidBlockIndexException` / `OperationCanceledException` and immediately
retries against the new tip instead of just logging. The handled exception is
no longer printed red (`Debug.LogException` is skipped for the benign
tip-race/`OperationCanceledException` cases, which log a plain
"Tip changed while mining. Retrying against the new tip." line instead), so
the Console / player log stays clean while the retry still runs in both the
Editor and the built player.

### 4. Late joiners: `ChainIdNotFoundException` on preload

A `--no-miner` node with a fresh store has no canonical chain, and
`PreloadAsync` internally forks from the genesis common point, which throws
`ChainIdNotFoundException` for a genesis-only store. Two mitigations:

- `Agent` appends the genesis block at init when the store is empty.
- Preload failure is now **non-fatal** (logged, swarm still starts). Practical
  recipe: seed a joining node's `--storage-path` with a snapshot of the seed's
  storage; the test script does this automatically.

**Topology note**: this game needs exactly one miner (the seed). If two peers
both mine, competing blocks fork the chain and tx-carrying blocks get orphaned;
run every non-seed node with `--no-miner`.

## Two-node test procedure

Automated: `powershell -ExecutionPolicy Bypass -File planet-clicker\run-two-nodes.ps1`
(generates keys, launches A + B from the existing build, snapshots storage,
waits, verifies, prints PASS/FAIL, leaves `pc_test_A.log` / `pc_test_B.log`).

Manual equivalent:

```powershell
# 1. Generate two distinct keys (any secp256k1 key works, 32 random bytes).
# 2. Launch Node A (seed + miner):
PlanetClicker.exe --private-key <keyA> --port 39710 `
  --storage-path C:\pc\nodeA -logFile C:\pc\A.log
#    Wait for: "The address of this node: <pubkey>,127.0.0.1,39710"
# 3. Copy C:\pc\nodeA → C:\pc\nodeB (storage snapshot), then launch Node B:
PlanetClicker.exe --private-key <keyB> --port 39711 --no-miner `
  --peer "<pubkeyA>,127.0.0.1,39710" `
  --storage-path C:\pc\nodeB -logFile C:\pc\B.log --auto-click
# 4. Check: B's add_count txs appear in A's log (mined), and B renders
#    synced blocks. Distinct "Agent initialized. Address:" lines prove
#    distinct identities without Product Name changes or AppData edits.
```

### Verification excerpt from the passing run

Two instances of the **same build**, distinct sign-in keys, one machine:

```
A: Agent initialized. Address: 0x3c6cCBE1466C4BEA93ED1d165585180C93ac3Cda, Host: 127.0.0.1, Port: 39710
B: Agent initialized. Address: 0x1edD305dD07EbF0C20bf6fc3d17C6fc8a467a243, Host: 127.0.0.1, Port: 39711, Seed peers: 1

A (miner, executing B's transactions): add_count: CurrentCount: ... 360 (cumulative, kept climbing)
B (synced, rendering A's blocks):      add_count renders: 129 and growing
A tip: created block index: 682, difficulty: 186652
```

Ranking state (`RankingState`) is updated by the same `AddCount.Execute` on
every node, so both nodes' leaderboards include both addresses once synced.

## Known limitations / next steps

- The sign-in scene uses default Unity/TMP control styling over a dark panel —
  close enough structurally to the reference (Address → Secret → Sign-in), but
  not the pixel art. Drop-in prettifying only touches `SignInSceneBuilder`.
- Keystore entries are per-Windows-user (`Web3KeyStore.DefaultKeyStore`); a
  custom per-node keystore directory would need a `Web3KeyStore(String)` overload.
- `--ice-servers` remains unimplemented (was never implemented here); STUN is
  irrelevant for loopback testing and can be added to `Options` the same way if
  LAN/NAT traversal is needed later.
- If Libplanet upstream fixes genesis-only preload forks, the storage-snapshot
  step in the test script becomes unnecessary.
