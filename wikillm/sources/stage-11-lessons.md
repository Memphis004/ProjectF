# Stage 11 — Real-chain E2E: seed node + hub + Buy/Sell/Craft (lessons)

Stage 11 closes the loop: the Unity client now plays against a REAL
Libplanet seed node (127.0.0.1:31236, ~2s blocks) + HubServer (5170, h2c)
through the whole economy — create_avatar → shop BUY → fish → SELL →
UNLOCK KITCHEN → craft — with every step asserted against the CONFIRMED
StateWatcher snapshot. Same contract as previous stage docs: what shipped,
what broke, and the traps worth keeping.

## Shipped

- **Salt in the shop** (data fix): `data/shop.csv` row `,10,6001,3,0,1` —
  salt 6001 @ 3g, unlimited, lvl 1. Table row-count asserts 9→10 in
  `TableDataTests` + `TablesRoundTripTests`. Craft (recipe 1) needs fish
  3001 + salt 6001, so without this row the craft loop dead-ends.
- **`unlock_kitchen_v1`**: flat 50g fee, one-time (re-unlock throws
  InvalidOperationException), empty payload Dictionary, SyncStamina stamp,
  avatar must exist, EnsureOwner. 5 lib tests. Loc keys
  KITCHEN_UNLOCK/KITCHEN_UNLOCKED (th/en), CraftWindow view gained
  `unlockButton` (SerializeField) + `KitchenPresenter.UnlockAsync()`; the
  generator places the button ON the LockedOverlay and wires it via
  SerializedObject property name. CraftWindow prefab regenerated by full
  setup — `UnlockButton` node + wired `unlockButton` field verified in the
  .prefab text.
- **Three client bootstrap bugs** (all found by the E2E, all fixed):
  1. `BootstrapCoreAsync` ran on a threadpool but touched
     `Application.persistentDataPath` (KeyStore + resolved paths) → threw →
     permanent offline read-only mode. Fix: pre-resolve storePath /
     genesisPath / hubAddress / nodePort / keysDir on the MAIN thread, pass
     into the Task.Run body.
  2. `Directory.CreateDirectory(storeDir)` lost in a refactor — restored.
  3. `DefaultStore.GetCanonicalChainId()` returns **Guid.Empty (not null)**
     on a fresh store → ctor threw "Given store does not contain chain id
     00000000…". Treat `null || Guid.Empty` as no-chain →
     `ListChainIds().FirstOrDefault()` (skip Guid.Empty) → else null →
     `BlockChain.Create`.
- **THE session bug — the swarm timeout CTS killed BOTH gossip and
  catch-up**: `_swarmCts = new CTS(TimeSpan.FromSeconds(max(30,
  SyncTimeoutSeconds)))` was a time bomb on the WHOLE swarm session. On a
  long initial sync (fresh client store pulling 1200+ blocks at ~2s/block
  ≈ 40+ min of chain), `PreloadAsync` was aborted mid-catch-up with
  OperationCanceledException → VContainer surfaced it → AppBootstrapper
  died before HUD/scene routing (game silently stuck on a black-ish editor
  state, no `[boot]` lines). And even when bootstrap finished, gossip died
  at the timeout: client fell off the seed mid-session (Peers 0) with no
  error. Short chains (~500 blocks last session) fit under 120s and MASKED
  both bugs. Fix: gossip CTS has NO timeout (lifetime token; shutdown via
  teardown); PreloadAsync gets a per-pass `CreateLinkedTokenSource(ct)` +
  `CancelAfter(max(300, SyncTimeoutSeconds))`, and a pass-budget expiry is
  CAUGHT (`when (!ct.IsCancellationRequested)`) and logged as "resuming
  catch-up" — the 3-pass loop continues from the new tip.
- **Buy used ITEM id instead of SHOP ENTRY id**: ShopPresenter passed 1001
  (item) where the chain wants the TbShop row id 1 (`Shop entry 1001 is
  not in the game tables` on-chain at block #532). Fix:
  `ShopEntryIdFor(GeneratedTables, itemId)` maps via TbShop.DataList; the
  same bug existed in the TEST script itself (BuyItemAction(1001,…)) —
  the UI and the harness were wrong in the same way.
- **Test flow correctness**: the pond pool is WEIGHTED (3001 weight 90 vs
  3002 weight 100 + 3003/3004) — counting only 3001 catches hid ~69% of
  hits as invisible bycatch ("0 fish in 24 casts" that was actually 13
  hits). And selling the only 3001 starves the craft phase. Final flow:
  fish until (2× 3001) or (1× 3001 + bycatch), confirm each cast via
  FishingExp movement (moves on every cast — miss grants 1 exp), sell
  bycatch preferentially, tolerate the already-unlocked kitchen on reruns
  (chain state persists across sessions — reruns must be idempotent).

## Traps worth keeping

- **Seed node embeds tables at BUILD time.** GameTables.Instance is baked
  into ProjectF.Lib; `dotnet run --no-build` after a data change runs the
  OLD tables (it rejected `buy_item` entry 1001 — and would have rejected
  the valid entry 10). After ANY data/ or lib change: rebuild the seed
  (`dotnet run` WITHOUT --no-build, or explicit `dotnet build`) and
  restart it; the chain store persists, so nothing else resets.
- **Chain state persists across test reruns.** The avatar, gold, unlocked
  kitchen, inventory all live in `.freebuff/chain`. A rerun that re-sends
  unlock_kitchen_v1 correctly FAILS (one-time guard) — tests must check
  `watcher.Current.KitchenUnlocked` first and skip the tx. Wipe only the
  CLIENT store (`%USERPROFILE%/AppData/LocalLow/DefaultCompany/UnityProject/
  chain-player1`) to force a full resync; keep `keys/player1.hex` so the
  same address re-attaches to the same avatar.
- **Fixed sleeps lose to chain latency.** A 1.1s (2-poll) wait after
  SubmitWithReasonAsync raced the block arrival — buy showed gold
  300→300. Poll the SNAPSHOT until the expected delta appears
  (`WaitSnapshotAsync(watcher, s => …, timeoutMs)`), 250ms steps; exp
  movement is the reliable per-cast fishing signal.
- **The snapshot can ALSO lag its own event**: Phase 0's assert right
  after the watcher polled showed name= gold=0 stamina=0 while the chain
  already had E2E/300 — a later probe showed the correct values. Never
  trust a single read; poll a predicate.
- **An editor restart RESETS Editor.log** (fresh header) — grep counts
  from before the restart silently miss. After any editor crash/restart,
  re-grep from scratch and re-verify markers ("entering play", bootstrap
  lines) belong to the CURRENT run. Domain reloads also race the MCP CLI:
  "Failed … after 10 retries" right after a refresh → wait and re-dispatch.
- **PreloadAsync on 5.5.3 is `(IProgress<BlockSyncState>?, CT)`** and can
  complete early on long chains — hence the 3-pass loop. `BlockHash` has
  no `!=` — compare via `.Equals`. `Integer.Value` is a BigInteger —
  `(long)` cast when reading Bencodex values.
- **Play-mode infra**: seed via
  `nohup dotnet run --project src/ProjectF.SeedNode --no-build -c Debug --
  --SeedNode:PrivateKeyHex=$(cat .freebuff/seed_key.hex)
  --SeedNode:StorePath="$(pwd -W)/.freebuff/chain" --SeedNode:IsMiner=true
  > .freebuff/seed.log 2>&1 &` (BACKGROUND process_type not implemented —
  nohup works); hub likewise on 5170. Check `grep -a "[status]"
  .freebuff/seed.log | tail -1`. Kill via the PIDs from
  `netstat -ano | grep -E ":(31236|5170)" | grep LISTEN`. Payloads are
  built by `node .freebuff/e2e/build_payloads.js <name>` FROM REPO ROOT
  (paths inside the script are repo-relative) and dispatched with
  `npx unity-mcp-cli run-tool script-execute --input-file
  .freebuff/e2e/p_<name>.json UnityProject`.

## Phases 5–6 + sync HUD postscript (same session, second commit)

- **E2E grew to 8 phases** (0 create_avatar, 1 buy, 2 fish, 3 unlock, 4
  craft, 5 EAT, 6 TASKBOARD reroll+submit, ALL PASS at tip #3381). Eat
  asserts food −1 AND stamina non-decreasing — the exact +15 is polluted by
  the 1/block SyncStamina regen, so "restore ≥ 0, capped" is the honest
  delta. Taskboard: the 600-block lazy reroll gate means a rerun may find a
  LIVE board — reroll only when `Tasks.Count == 0` or
  `BlockIndex − TasksLastRerolledAt >= 600`; pick the first incomplete task
  (prefer one already satisfiable), source materials by category (fish
  3001–3009 → cast loop with bait top-up; food 7001–7009 → recipe 1 after
  sourcing fish+salt; else shop), assert gold + RewardGold exactly and the
  board flag flips to done.
- **Swarm.Peers is IReadOnlyList<BoundPeer> — there is NO per-peer tip on
  it.** `PeerState.BestKnownTip` does not exist in 5.5.3 (CS0030/CS1061
  within one refresh). The peer-tip API is
  `await swarm.GetPeerChainStateAsync(dialTimeout, ct)` →
  `PeerChainState.TipIndex` (verified against docs.libplanet.io/5.5.3 —
  no XML docs ship with the DLLs).
- **Sync HUD (kiosk-free)**: `ILibplanetClient.SyncProgress` (Tip /
  TargetTip / HasTarget — display-only struct) fed by a 1s background
  sampler that adopts the highest peer tip (`Volatile.Write`; failures are
  swallowed — cosmetic only). `HudPresenter` gained an `ILibplanetClient`
  ctor param and a 500ms poll loop rendering the SyncLabel (top-center):
  "Syncing N / M" ONLY while HasTarget (behind the peer tip), plain
  "Syncing" while Bootstrapping, HIDDEN at rest — plus it now drives
  SetChainStatus (nothing else did). VContainer auto-injects the root-
  registered client into the 4 scene scopes — no registration edits.
  Generator adds the SyncLabel row + wires `syncLabel`; loc key
  UI_SYNC_PROGRESS ("ซิงค์ {0} / {1}"). Verified: probe at rest shows
  `tip=3457 target=3456 hasTarget=False`, 0 NREs after a full catch-up.
- **A second Unity instance silently fights for the project.** Mid-session
  the MCP CLI degraded to "Failed … after 10 retries" while a hidden
  duplicate editor held the lock. Fix: kill ALL Unity.exe, remove
  Temp/UnityLockfile, relaunch ONCE; then check the log for stale-tag
  discipline again (fresh session = fresh Editor.log).
- **CI**: `tools/ci-chain-e2e.sh` — builds seed+hub (embed tables!), boots
  them via nohup, wipes the client store, enters play, polls Editor.log for
  "bootstrap done" (up to 30 min), dispatches the harness, verdicts on the
  post-dispatch `[ce2e]` tail (line-offset capture so reruns never confuse
  runs), tears down by port PID. Flags: SKIP_BOOTSTRAP=1 (reuse running
  infra), TEARDOWN=0 (keep alive for debugging). Exit 0 only on ALL PASS.
